# 체계적 커버리지 체크리스트 (3차 스윕용)

성격별 7묶음으로 나눠 각 에이전트가 병렬로 스윕한다. **이미 발견된 이슈 목록을 각 에이전트에 주입** → 신규만 집중(중복 억제).

## 클러스터 1 — 에러 처리 · 외부응답 · 사용자대면 에러
- 에러 처리 확인 - 예외를 조용히 삼켜 장애를 숨기지 않는지, 재시도로 풀릴 오류와 아닌 오류를 구분해 처리하는지, 죽으면 안 되는 경로(렌더·응답 조립·폴백)에서 라이브러리/외부가 던질 수 있는 예외를 형제·파생 예외까지 빠짐없이 방어하는지(한 예외 클래스만 잡고 유사 예외를 놓치지 않는지)
- 외부 응답의 다중 전달 경로 처리 - 외부(백엔드·서드파티) 호출의 성공·실패가 여러 형태(정상 응답 + 실패 body / 예외 / 상태코드)로 올 수 있을 때 모든 경로를 대칭으로 처리하는지, "어떤 형태로 오는지"에 대한 가정을 문서·실측으로 검증했는지(한 경로만 처리하고 나머지는 generic 오류로 새지 않는지)
- 사용자 대면 에러 분리 - 사용자에게 반환되는 에러가 내부 구현 상세(원문 예외 메시지·경로·쿼리·내부 계약 문구)를 노출하지 않는지, 내부 진단 로그와 사용자용 메시지를 분리하고 사용자 문구는 언어 정책을 따르는지
- 예상 가능한 실패의 상태코드 매핑 완전성 - 정상적인 도메인 실패(미가입·권한 없음·대상 없음·중복 등)가 generic 5xx로 새지 않도록, 호출 스택에서 발생 가능한 예외 타입을 빠짐없이 포착해 의미 있는 상태코드/안내로 매핑하는지

## 클러스터 2 — 동시성/비동기 · 리소스 · 배포내구성 · 재시도 · DB
- 동시성·병렬처리 - race condition, 락/데드락, 트랜잭션 격리, 부분 실패 처리가 안전한지 (특히 동시 쓰기 정합성)
- 프로세스 로컬 상태의 배포 내구성 - in-memory·프로세스 로컬 상태(세션·대기작업·캐시)가 다중 워커·오토스케일·재기동에서 유실·불일치되지 않는지, 외부 저장소·sticky 라우팅·락으로 보장하거나 단일 프로세스 가정을 명시했는지
- 비동기 코드에서 동기 I/O를 직접 호출해 이벤트 루프를 블로킹하지 않는지
- DB - 파라미터 바인딩(SQL Injection 차단), N+1·인덱스, 트랜잭션 경계, 커넥션 누수 여부
- 단건 조회의 결정성 - 단건 조회(fetchone·first·[0])가 다중 매칭 가능한 쿼리에서 정렬·제한(LIMIT) 없이 임의 행을 집지 않는지, 결정적 선택 기준이 있는지
- 리소스 정리 - 파일 핸들·스트림·스레드·커넥션이 확실히 닫히고, 작성한 정리 코드가 실제 호출 경로에 연결돼 있는지 (앱 startup에서 연 자원은 shutdown/lifespan/teardown에서 짝으로 닫히는지)
- 재시도·타임아웃·폴백 - 재시도 상한과 대기 시간 상한이 있는지, 타임아웃이 실제 처리 시간을 커버해 중복 처리·중복 과금이 없는지, 폴백 시 부분 성공 결과를 버리지 않는지

## 클러스터 3 — 보안
- 보안 - 신뢰 경계에서의 입력 검증, 인가(IDOR 등 본인 리소스 확인 — 조회뿐 아니라 재개·취소·재실행 등 상태전이 API에서도 요청자가 그 리소스의 소유자인지 검증, 응답에 타인 데이터·PII가 실리지 않는지), 로그·에러의 민감정보 노출, path traversal·업로드 검증. 클라우드 자격증명 실제 값 노출/api key 노출 검토
- 극한·악의적 입력에 견디는지 - 재귀 깊이, 무한 루프, 크기 제한 없는 로드로 인한 자원 고갈(OOM) 방지
- 부분 문자열 매칭 오탐 - 코드·식별자·상태 판정에서 경계 없는 substring 매칭이 유사 값을 오탐하지 않는지 (정확 매칭·단어 경계·파싱으로 판정)
- LLM 프롬프트에 신뢰할 수 없는 입력을 그대로 삽입해 인젝션에 노출되지 않는지
- api key, secret key, 클라우드 관련 config 값 등 노출 여부(노출되면 안 됨)
- 하드코딩된 환경 의존값(URL, 경로, 리전 등)이 설정으로 분리되어 있는지

## 클러스터 4 — 코드품질/구조
- magic number로 관리 가능한 것들이 있는지 확인
- 반복되는 고정값·문자열을 상수나 enum으로 관리하고 있는지
- 사용하지 않는 파라미터를 불필요하게 인자로 받고 있는지
- 중복 코드는 없는지
- 간소화할 수 있는 코드인데 불필요하게 장황하게 작성된 부분은 없는지
- 코드 일관성 (유사 역할 함수 간 처리 방식이 어긋나지 않는지 포함)
- 각 파일별로 역할/책임 분리가 잘 되어 있는지, 각 파일들이 목적에 맞는 디렉토리에 위치해 있는지
- 변수명이 직관적이지 않아 무엇을 의미하는지 알 수 없는 경우가 있는지
- 슬라이싱 검토 - 꼭 필요해서 자르는 건지 확인 필요
- 결과에 영향을 미치는 인덱싱/슬라이싱 존재 여부 - 전체 데이터가 필요할 수 있는 부분에서 인덱싱과 슬라이싱이 들어가면 결과에 영향을 줄 수 있음 (로깅 제외)
- 목적 달성을 위해 불필요하게 복잡한 방식이 적용되지 않았는지 확인 필요

## 클러스터 5 — AI 잔재 · 주석/docstring
- AI 생성 코드 특유의 잔재(도달 불가 코드, deprecated 관용구, 리팩토링 후 죽은 코드)가 없는지
- 주석·docstring이 현재 코드 동작과 일치하는지
- 불필요하게 장황한 주석 - 개발/실험 과정이 드러나는 부분(코드에 티가 날 필요가 없음), 리뷰 반영 과정 및 개발 과정에서 편의상 붙인 넘버링/분류 등이 드러나는 부분, 작업 일자가 드러나는 부분, 과도하게 상세한 주석 등 불필요한 주석은 제거 대상

## 클러스터 6 — 과금/관측 · i18n · 의존성 · 캐싱 · 테스트 · API 설계
- 과금·관측 - LLM이 사용되는 모든 단계에 대해 토큰 사용량이 정확히 집계되는가. 과소/과도 과금 처리 되지 않는가(사용하지 않는 건에 대한 과금, 사용한 건에 대한 과금 누락), 중복 과금은 없는가
- 관측성 - 장애 추적에 필요한 로그·메트릭이 적절한 레벨로 남는지(과다 로깅 포함), 폴백·예외 경로도 사후 식별 가능하게 남는지
- 다국어·로케일 - 기본 언어 처리가 정책과 일치하고 한 곳에서 관리되는지, 언어별 특수 처리가 반영됐는지(전각/반각·IME 기본 문자 등 유니코드 변형 입력 정규화 포함)
- 의존성 버전이 재현 가능하게 고정(상한 포함)되어 있는지
- 캐싱 - 캐시 무효화·최신값 갱신이 의도대로 동작하는지
- 테스트 - 변경분·엣지케이스·실패 경로를 커버하되, 실제 코드 경로를 실행해 코드가 깨지면 실패하는 유효한 테스트인지. 여러 규칙·조건·플래그가 동시에 성립하는 조합과 그 우선순위(중재)까지 검증하는지(각 조건 단독만 테스트하고 동시발동을 빠뜨리지 않는지)
- 레지스트리·병렬 목록·분기 기본값의 완전성 - 같은 성격의 항목 집합(레지스트리 행, 턴 초기화/리셋 목록, else 기본값 등)을 전수 대조해 일부 항목만 누락·불일치하지 않는지, 규약 위반을 불변식 테스트로 고정하는지 (예: read_only=False면 impact_fn 등록 필수, 초기화 목록에 신규 상태 필드 포함 필수)
- API 설계 - 상태코드/스키마 일관성, 멱등성, 페이지네이션, 하위 호환성이 적절한지

## 클러스터 7 — 외부 의존성 실체 검증
- 라이브러리/SDK 기본값(timeout·max_retries·backoff 등)을 그대로 쓰는 경우, 그 기본값을 설치된 버전의 소스/상수로 실제 확인했는지, 상위 계층 제약(큐·요청 타임아웃 등)과 모순되지 않는지 (예: SDK read timeout > 상위 큐 timeout → 소켓 누수)
- 외부 응답 스키마·필드 접근이 설치된 버전에 실제 존재하는 필드인지 (버전별로 사라진/이름 바뀐 필드를 참조해 항상 빈값·None이 되지 않는지)
- 외부 라이브러리에 대해 코드/주석/docstring이 주장하는 동작(기본값·응답 형태·필드 유무)이 실제와 일치하는지 — 특히 AI가 생성한 라이브러리 관련 주석은 근거 없는 서술로 의심하고 검증
- 검증은 코드 읽기 + **공식 문서/릴리스노트 웹서치**로 근거를 확보(버전 명시). 기억/추측 금지
